# Decisions

One line per product or technical decision and why. Newest at the bottom.

| Date | Decision | Why |
| --- | --- | --- |
| Nov 24 | Build lives in `launch-control/` inside the `Austinjw` repo on branch `claude/sleepy-keller-uwwoh3`, not a new `launch-control` repo | The build session's GitHub access is scoped to that one repo and can't create repos. The folder is self-contained, so it can be moved to its own repo (or deployed from Vercel with Root Directory = `launch-control`) without changes. |
| Nov 24 | Next.js 16 App Router, React 19, TypeScript 5.9 (not 7) | Latest stable Next. TypeScript 7 (native compiler) is new enough that Next's type-check step is a risk; 5.9 is the safe choice for a demo build. |
| Nov 24 | All domain dates are ISO calendar dates (`YYYY-MM-DD`); scoring takes `asOf` as an input instead of reading the clock | Linear returns absolute dates, the prototype used day offsets. Calendar dates make the rules pure, timezone-free and testable on any date, and the same functions serve both adapters. |
| Nov 24 | The tracker API takes the browser's local date (`?today=`), trusted only within ±1 day of server UTC | The prototype's dates are relative to the viewer's today. A Vercel server runs in UTC, so in US evenings its "today" is tomorrow; without this the demo would shift a day. The clamp stops arbitrary dates. |
| Nov 24 | Every snapshot carries its own `asOf`; UI, rules brief and (later) agent all score against it | One source of "today" per load, so the headline, gates and brief can never disagree. |
| Nov 24 | Gate rule ported exactly: no ticket → blocked → overdue → due after go/no-go, first match is the reason shown; due *on* go/no-go day is not a risk | Matches the prototype and the PRD wording ("due after"). Covered by unit tests, including the L1 = 3 of 10 at risk expectation. |
| Nov 24 | Overdue means due date before today; due today is not overdue | Same as the prototype (`due < 0`). |
| Nov 24 | `rulesBrief`, `boardSummary`, `hygieneChecks`, `autofix` are pure functions returning new data | Lets the UI, the API and the agent's tools share one implementation and keeps tests trivial. |
| Nov 24 | Briefs are parsed into plain data and rendered as React text nodes; no `dangerouslySetInnerHTML` anywhere | CLAUDE.md: Claude output and Linear text are untrusted. The prototype escaped HTML by hand; React does it by construction. |
| Nov 24 | Copy exec update strips `**bold**` markers and stops at the next heading | Paste-ready text for Slack or email; the prototype copied raw Markdown. |
| Nov 24 | Default selected launch is the headline's at-risk launch (L1 on demo data), not a hard-coded `L1` | Same result on demo data, and still sensible on live Linear data where IDs differ. |
| Nov 24 | Tracker fetch has a 5 s timeout; if `/api/tracker` fails, the browser builds the demo snapshot itself and shows a banner | PRD §6: the app always works on first load and says when it fell back. |
| Nov 24 | Added a fallback banner style (pink-edged note) that the prototype didn't have | PRD requires a visible banner; styled with the prototype's risk colour so it reads as part of the same system. |
| Nov 24 | Calendar bars clamp at 0 days (past launch dates) as well as at the 35-day axis | Live Linear data can contain launches whose date has passed; the prototype never did. |
| Nov 24 | Hanken Grotesk via `next/font` (self-hosted at build) instead of a Google Fonts `<link>` | No runtime request to Google, no layout shift, works offline at the interview. |
| Nov 24 | CSS: element styles in `app/globals.css`, everything else copied from the prototype into one CSS module (`components/lc.module.css`) | CLAUDE.md asks for CSS modules with the prototype as the style guide; one file keeps it diffable against the prototype. |
| Nov 24 | In M1 the brief button reads "Run readiness check" and uses the rules engine with the prototype's "Claude is not available" trace | That is the prototype's own no-Claude behaviour; M2 swaps in the agent. |
| Nov 24 | `seed-build-project.ts` supports `--dry-run` and needs `--yes` to write | Writing to Linear needs Austin's go-ahead; the dry run shows exactly what would be created first. |
| Nov 24 | Build-project issues get Gate labels (eng/qa/docs/comms) if they exist, but no Tier label | Keeps the build project out of the launch calendar until we decide the PRD open question about showing it in the demo. |
| Nov 24 | Ran `seed-build-project` against Linear team LCH (Austin approved): project + LCH-1…LCH-12. Re-run confirmed idempotent | Dogfooding PRD §8. Note for M3: Linear assigns identifiers itself, so seeded demo issues will not be LCH-101 etc.; tests on live data must key on titles, not IDs. |
| Nov 24 | M2 agent is a manual streaming tool-use loop (`client.beta.messages.stream`), not the SDK's beta tool runner | Needed exact control over the 6-tool-turn cap and to emit a `tool` SSE event per call for the live trace. After 6 tool turns the last call runs with `tool_choice: none` so Claude still writes a brief instead of failing. |
| Nov 24 | Model `claude-sonnet-5-5` (as the PRD specifies), effort `medium`, adaptive thinking left on | Measured ~6–7 s for a full L1 brief with 2 tool calls, well under the 30 s target; `medium` kept the brief specific without slowing it down. |
| Nov 24 | Server-side refusal fallback on (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) | If a safety classifier declines, the API retries on a fallback model in the same call instead of the demo dropping to the rules brief. If the whole chain still refuses, we show the rules brief with code `refusal`. |
| Nov 24 | In demo mode the browser POSTs its current snapshot to `/api/brief`; the server validates it strictly (`lib/tracker/validate.ts`) | The demo edits tickets in memory (status pills, auto-fix) and the agent must see what's on screen, as in the prototype. Validation bounds size and drops unknown fields, so posted data can only ever be data. Linear mode (M3) will load server-side instead. |
| Nov 24 | Added one line to the ported agent prompt: "Use only these four headings, in this order, and add nothing after the exec update." | First real run added an extra unrequested section after the exec update. With the line, output followed the format exactly. |
| Nov 24 | 45 s server deadline, 50 s browser deadline; any failure (no key, auth, rate limit, timeout, refusal, empty) → rules brief with "Claude didn't answer (code)" in the trace | PRD §6. The browser waits slightly longer than the server so the server's specific error code arrives instead of a generic timeout. Verified with no key and a bad key. |
| Nov 24 | `GET /api/brief` reports only whether a key is configured; the button says "Run readiness agent" or "Run readiness check" accordingly | The key never reaches the browser, and the UI is honest about which engine will answer. |
| Nov 24 | Server logs only `[brief] <launch> failed: <code>`; never prompts, payloads or keys | CLAUDE.md: secrets never in logs. |
| Nov 24 | M3: the Linear mapping lives in one file (`lib/tracker/linear-schema.ts`) used by both the seed script and the adapter | PRD §9 risk "Linear model doesn't map cleanly": the writer and reader can't drift apart. |
| Nov 24 | Sample-org people are stored as text: `Owner: Name` in the issue description, `PM: Name` in the project description, `Lead: Name` in the Function label description; a real assignee or project lead always wins | The fictional owners aren't Linear workspace members, so they can't be assignees. Without this, live mode would show every issue unowned and hygiene would be meaningless. Real use (actual assignees) works unchanged. |
| Nov 24 | The seed added two workflow states to team LCH: In Review and Blocked | The team had neither. The PRD maps Blocked to a state or a `blocked` label; the adapter accepts both, but a real state looks right in Linear during the demo. |
| Nov 24 | Function labels for QA, Docs and Support are named "QA team", "Docs team", "Support team" | Linear label names are unique per team ignoring case, so they collided with the `qa`, `docs`, `support` gate labels the PRD specifies. The mapping file translates them back. |
| Nov 24 | A launch is a team project with a `Tier N` project label and a target date; issues in other projects (e.g. the "Launch Control v1" build project) are ignored, issues in no project count as unlinked | Keeps the build's own tickets off the launch calendar and out of hygiene, while still flagging stray tickets. |
| Nov 24 | Live launch ids are Linear project slugs; the agent's trace shows the launch name for them | Slugs are stable across reloads; "get_gates · 7e2477…" read badly on screen. |
| Nov 24 | The adapter reads Linear with 3 small GraphQL queries in parallel (projects, labels, paged issues) via the SDK's `rawRequest`, 5 s overall timeout | One big query exceeded Linear's complexity limit; the SDK's lazy relations would be ~100 round trips. Measured ~300 ms for the seeded team. |
| Nov 24 | Live mode is read-only in the UI: no status cycling, no auto-fix (M4 adds confirmed hygiene fixes); issue ids link to Linear | The prototype's status pills edit local demo data. In live mode a local-only edit would silently diverge from Linear. |
| Nov 24 | In Linear mode the agent's snapshot is loaded server-side, not posted by the browser | The brief should reflect the tracker of record; posted data is only trusted in demo mode. |
| Nov 24 | Data source choice is remembered per browser; demo stays the default for new visitors; any Linear failure falls back to demo data with a banner saying why | PRD §6 and CLAUDE.md "demo data is the default source". Verified with a bad key and a missing key. |
| Nov 24 | Known difference: right after seeding, "No update in 14+ days" is 0 in Linear (4 in demo) | Linear sets `updatedAt` itself; the seed can't backdate it. Gate scoring, headline and the rest of hygiene match exactly (`npm run check:linear`). |
| Nov 24 | M4: one rules function, `proposeFixes`, drives both demo auto-fix (applied in memory) and Linear fixes (applied on the server) | Same rules, same log lines in both modes; demo tests pinned the behaviour through the refactor. |
| Nov 24 | Linear fixes: the browser sends only fix ids; the server reloads Linear, recomputes proposals and applies only ids that are still proposed | A stale or tampered request can't write anything the rules wouldn't (verified: re-sending an applied fix is skipped). Max 50 per request. |
| Nov 24 | Confirmation is a review list: every proposed change is listed and ticked; "Apply N to Linear" writes only the ticked ones | PRD §4.5 "Apply writes them to Linear after confirmation". A per-fix opt-out is more useful in a live review than one yes/no dialog. |
| Nov 24 | What each fix writes: owner → assignee if the lead is a workspace member, else the `Owner:` description line; due → issue due date; stale → a comment on the issue asking the owner for a status before go/no-go | Mirrors the demo's three fixes with real Linear actions. A comment is a genuine nudge (the owner gets notified) and it also refreshes `updatedAt`. |
| Nov 24 | Writes run one at a time, 5 s timeout each; one failure doesn't stop the rest; each result is logged (3 min saved per success, failures logged at 0) | Partial success is reported truthfully instead of all-or-nothing. Measured ~2 s for 4 fixes. |
| Nov 24 | `/api/hygiene/apply` requires `DEMO_PASSCODE` in an `x-demo-passcode` header whenever that variable is set | It writes to Linear from a public URL. M5 adds the passcode prompt in the UI; until then leave `DEMO_PASSCODE` empty locally. |
| Nov 24 | `npm run seed:linear -- --restore --yes` resets seeded issues' owner line, due date and status to the seed | After one live apply there's nothing left to fix; rehearsals need a reset. Nudge comments are left in place (deleting data is out of scope). |
| Nov 24 | M5: one `guard()` for both paid/writing endpoints — rate limit first, then passcode | Counting wrong passcodes against the limit stops guessing for free. Passcode compared as SHA-256 digests with `timingSafeEqual` (no length/timing leak). |
| Nov 24 | Rate limit: 10 agent runs/hour, 20 apply requests/hour per IP, in memory | PRD's suggested number. On Vercel each instance counts separately, so it's a cost brake, not an exact quota; the Anthropic spend limit is the hard cap. No database (PRD non-goal). |
| Nov 24 | Passcode asked once per browser session (sessionStorage), before the agent starts, re-asked on a 401 | No account system (PRD non-goal). Asking before "Agent is reading…" avoids a run state with nothing running; cancelling changes nothing. |
| Nov 24 | Rate-limited or offline agent runs fall back to the rules brief with the reason in the trace ("rate limit… try again in N min", "offline") | Same fallback contract as every other Claude failure: the review never stalls, and the screen says why. |
| Nov 24 | Added recommendation thresholds to the agent prompt (NO-GO if any gate is at risk; GO WITH CONDITIONS if none at risk but some in progress; GO only if all ready) | Smoke test caught Claude saying GO WITH CONDITIONS with 2 gates at risk. The AI and rules briefs must never disagree on the call in front of an exec; Claude adds the judgment in the reasons. |
| Nov 24 | Empty state: "No launches on the calendar yet" explains what counts as a launch | Previously an empty Linear team would have read "Every launch is on track", a false all-clear. |
| Nov 24 | `app/error.tsx` error screen with "Reload with demo data" | Last resort for an unexpected crash on stage: never a blank page, one click back to the default that always works. |
| Nov 24 | `npm run smoke` (Playwright, pinned 1.63.0) walks the demo script against any URL and fails loudly; never writes to Linear | The QA gate is "3 clean runs on the production URL"; a script makes that repeatable and checks the agent/rules agreement too. |
| Nov 24 | Agent loop extracted to `lib/agent/run.ts`, used by both `/api/brief` and the eval | The eval measures exactly what the app runs: same prompt, tools, model, effort and turn cap. |
| Nov 24 | Every fresh AI brief is checked in the UI: cited issue IDs must exist; the call must match the rules engine. Shown with run time and tool calls | Treats model output as untrusted and makes that visible. It's the in-product answer to "how do you know it's right?". |
| Nov 24 | `npm run eval`: 2 scenarios × 5 launches × 3 runs, scored on call agreement, invented IDs, at-risk recall and format | Fresh demo data has only one launch at risk; the "a week later" scenario moves five tickets so four launches are at risk for different reasons. First run: 30/30, 0 invented of 152, 21/21 recall, p50 5.3 s, $0.40 total. |
| Nov 24 | Launches whose date has passed drop off the calendar | Seeded Linear dates are fixed; by interview day one launch would have shown as 2 days in the past. A calendar that runs from today shouldn't show shipped launches. |
| Nov 24 | `seed:linear --restore` also re-dates the 5 launch projects (and takes `--as-of`); `check:linear` suggests it when dates drift | Found by scoring live data as of Nov 30: L1 would read 4 of 10 at risk and Knowledge Graph would go pink, so the "same scores" demo moment breaks. Verified by re-dating for Nov 30, checking, and re-dating back. |
| Nov 24 | Dogfood: "Launch Control v1" is a Tier 3 launch on the interview day (Nov 30), lead and assignee Austin; its eng/qa/docs gates are the build's real gate tickets | Answers the PRD's open question on screen. Launch Nov 30 puts go/no-go on Nov 28, the PRD's demo-ready date. The row is honest: it turns pink if the gates aren't closed in time. |
| Nov 24 | Risk alerts: one message per risky ticket (blocked, overdue, due after go/no-go) in an at-risk gate, to its owner, else the team lead, else the PM; gates with no ticket are reported, not messaged | Closes the loop from finding a risk to reaching the person who can fix it. Only the tickets that make the gate red are alerted, not the gate's other open work. |
| Nov 24 | Alerts use the same review-then-confirm flow as hygiene fixes (shared `ReviewList` + server-side `applyConfirmed`); posted as Linear comments; demo mode logs only | No new integration or key; reuses the tested guardrails (server recomputes, confirmed ids only, passcode, rate limit). A comment notifies the ticket's assignee and subscribers. |
| Nov 24 | No repeat alerts: the server skips a ticket that already has a Launch Control alert from the last 24 h; the page hides alerts sent this session | Chasing someone twice in a day erodes trust in the tool. Verified live: a resend was refused with "already alerted in the last 24 h". |
| Nov 24 | `--clear-comments` (opt-in, dry run by default) deletes only comments that start with the app's alert or nudge prefix | Rehearsals would otherwise make the live send hit the 24 h guard. Deleting data stays a deliberate human step. |
| Nov 25 | Leave-behind one-pager lives at `/one-pager` on the demo site, dark on screen and a single white page when printed | Same link as the demo, nothing extra to host or send; "Save as PDF" makes the attachment. Impact model shows its assumptions instead of claiming savings. |
| Nov 25 | Design polish on top of the prototype's look (colours, type and layout unchanged): branded top bar with the data-source switch; only at-risk gates expanded (in-progress ones collapsed, or expanded when nothing is at risk); risk alerts moved to a callout at the top of the gates panel; a go/no-go tick on every calendar bar; a pulsing working state while the agent runs | Fresh-eyes review: the page never said "Launch Control"; the gates panel ran ~1,400 px so the "close the loop" moment sat at the bottom; go/no-go, a core rule, wasn't visible on the calendar; and the agent's best moment showed plain "Thinking…". |
| Nov 25 | Go/no-go decision is recorded by a person under the brief and posted to Linear as a project update with a health flag (Go → on track, Go with conditions → at risk, No-go → off track) | Finishes the loop: find, brief, alert owners, decide, tell leadership. Uses Linear's own status mechanism (which can forward to Slack) instead of a new integration. |
| Nov 25 | A person may record a decision that differs from the rules; the update then states the rules' call and always carries the readiness numbers | The tool informs, a person decides. Making the override visible keeps that honest without blocking judgment. |
| Nov 25 | The decision update's numbers are recomputed on the server from fresh Linear data; only the decision, note and exec text come from the browser, length-bounded | Same stance as fixes and alerts: the screen can be stale, the record shouldn't be. |
| Nov 25 | A captioned 79-second walkthrough is generated by script (`npm run demo:video`) and served at `/demo.mp4` | Backup if the live demo fails, and a shareable asset for people who weren't on the call. Scripted so it can be re-recorded after any UI change. It never writes to Linear. |
